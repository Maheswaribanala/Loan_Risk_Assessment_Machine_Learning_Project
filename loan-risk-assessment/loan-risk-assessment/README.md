# Intelligent Loan Risk Assessment System

An end-to-end, full-stack Machine Learning web application that predicts whether a loan
applicant is **Low / Medium / High risk**, using a trained scikit-learn pipeline served
through a Flask REST API, with results stored and reviewable through a banking-style
admin dashboard.

Built as a Corner Stone Project — suitable for documentation, screenshots, presentation,
and viva voce.

---

## 1. Problem Statement

Manual loan-risk evaluation is slow, inconsistent between reviewers, and hard to justify
to applicants or auditors. Lenders need a fast, data-driven, explainable way to triage
applications before deeper manual underwriting.

## 2. Objective

Build a system that:
- Accepts an applicant's financial and personal details through a web form
- Engineers loan-risk-relevant features (DTI, loan-to-income, repayment capacity, etc.)
- Uses a trained ML model (selected by comparing Logistic Regression, Random Forest, and
  a gradient-boosted tree model) to classify the applicant as Low / Medium / High risk
- Returns a probability score and the leading factors behind the decision
- Persists every application + prediction to a database for audit and reporting
- Presents portfolio-level risk analytics on an admin dashboard

## 3. Real-World Application

- Pre-screening tool for loan officers before manual underwriting
- Consistent, auditable first-pass risk triage across branches
- Portfolio-level risk monitoring for management (dashboard)
- Educational reference implementation for an ML-backed decisioning system

---

## 4. Features

- Real-time risk prediction from a genuinely trained model (no hard-coded logic)
- Engineered financial features (DTI, LTI, EMI estimate, income stability)
- 3-model comparison (Logistic Regression, Random Forest, Gradient-Boosted Trees) with
  Accuracy / Precision / Recall / F1 / ROC-AUC / Confusion Matrix / 5-fold CV
- Automatic best-model selection by ROC-AUC (tie-broken by F1), not raw accuracy
- Hyperparameter tuning (RandomizedSearchCV) with a documented before/after comparison
- Basic explainability: global feature importance + per-applicant top contributing factors
- Class imbalance handled with SMOTE (oversampling on the training set only)
- Clean, validated REST API with proper error handling (no raw tracebacks)
- Banking/finance-themed, responsive, Bootstrap-based UI across 4 pages
- Admin dashboard: stat cards, pie chart, model-comparison bar chart, confusion
  matrices/ROC curves, feature importance, and full application history

## 6. Dataset Description

`dataset/loan_dataset.csv` — 6,000+ synthetic-but-realistic applicant records, generated by
`dataset/generate_dataset.py` using domain-informed rules (income by employment type,
credit score correlated with income/employment plus independent noise, loan amount scaled
to income, etc.), with injected missing values and duplicate rows so the cleaning steps in
the pipeline have real work to do.

> A public dataset (e.g. Kaggle's Loan Prediction dataset) could not be downloaded in this
> offline environment. To use a real dataset instead, drop a compatible CSV in as
> `dataset/loan_dataset.csv` (see `ml/feature_engineering.py` for the expected columns) and
> re-run `ml/train_models.py`.

**Raw columns:** applicant_name, age, gender, marital_status, education, dependents,
employment_status, self_employed, applicant_income, coapplicant_income, loan_amount,
loan_term, credit_score, credit_history, existing_loans, repayment_history, property_area,
risk_category (target).

---

## 7. Data Preprocessing

Implemented in `ml/preprocessing.py`:
- **Duplicates:** dropped via `drop_duplicates()`
- **Outliers:** income/loan-amount columns winsorized at the 1st/99th percentile (capped,
  not dropped, to avoid losing scarce high-risk examples)
- **Missing values:** median imputation for numeric features, most-frequent imputation for
  categorical features — done *inside* a scikit-learn `ColumnTransformer` so the exact same
  logic applies at prediction time
- **Encoding:** `OneHotEncoder(handle_unknown="ignore")` for categorical features
- **Scaling:** `StandardScaler` for numeric features

## 8. Feature Engineering

Implemented in `ml/feature_engineering.py` (imported by both training and the Flask
backend, so there is **no training/prediction mismatch**):

| Feature | Why it matters |
|---|---|
| `total_income` | Combined household repayment capacity |
| `monthly_repayment_estimate` | Amortization-based EMI estimate — lets the model reason about affordability, not just raw loan size |
| `debt_to_income_ratio` | Higher DTI = more income already committed = higher default risk |
| `loan_to_income_ratio` | Large loans relative to annual income signal over-leverage |
| `income_stability_score` | Employment type as a proxy for how predictable future income is |
| `credit_history` (binary) | Derived from credit score when not directly supplied; one of the strongest predictors of repayment behavior |

## 9. Database Design

**Specified:** MySQL, database `loan_risk_assessment`, tables `applicants` and
`predictions` exactly as described in the project brief. The full DDL is in
`backend/database/schema_mysql.sql`.

**As shipped:** `backend/database/db.py` uses Python's built-in `sqlite3` with an
**identical table structure** so the whole application is runnable immediately with zero
external services (no MySQL server was available in the build sandbox). Switching to real
MySQL is a 3-step change documented at the top of `db.py`:
1. `pip install mysql-connector-python`
2. `mysql -u root -p < backend/database/schema_mysql.sql`
3. Replace `_get_connection()` in `db.py` with a `mysql.connector.connect(...)` call — every
   other function already uses standard parameterized SQL.

**applicants**: id, applicant_name, age, gender, marital_status, education, dependents,
employment_status, self_employed, applicant_income, coapplicant_income, loan_amount,
loan_term, credit_score, credit_history, existing_loans, repayment_history, property_area,
created_at.

**predictions**: id, applicant_id (FK), predicted_class, risk_category, risk_probability,
model_used, top_factors (JSON), prediction_date.

## 10. ML Algorithms & Model Comparison

Three classifiers are trained and compared in `ml/train_models.py`:
Logistic Regression, Random Forest, and Gradient-Boosted Trees ("XGBoost" slot — see §5).

Metrics captured for each (test set + 5-fold stratified CV): Accuracy, Precision (weighted),
Recall (weighted), F1 (weighted), ROC-AUC (weighted, one-vs-rest), confusion matrix, ROC
curve. Results are written to `ml/model_comparison.csv` and plots to `ml/plots/`.

**Selection rule:** the best model is chosen by **ROC-AUC first, F1 as tie-break** —
deliberately *not* raw accuracy, since accuracy is misleading on an imbalanced 3-class
target even after SMOTE rebalances the training set.

## 11. SMOTE Implementation

Applied to the **training split only** (never the test set) after preprocessing, via
`ml/smote_custom.py` — a from-scratch multi-class SMOTE using k-nearest-neighbor
interpolation within each minority class, matching `imbalanced-learn`'s `.fit_resample(X, y)`
interface. See §5 for why a custom implementation was needed here and how to swap in the
real library.

## 12. Hyperparameter Optimization

The best model from the initial comparison is re-tuned with `RandomizedSearchCV` (5-fold
CV, scoring = weighted F1) over a model-specific parameter grid. Before/after metrics are
saved to `ml/tuning_before_after.csv`, and the tuned model only replaces the original if it
is not worse.

## 13. Explainability

- **Global:** top-15 features by `feature_importances_` (tree models) or mean absolute
  coefficient (Logistic Regression), saved to `ml/feature_importance.json` and shown on the
  dashboard.
- **Per-applicant:** the prediction result page shows the applicant's own values for the
  fields that rank highest in the global importance list — a simple, transparent way to
  explain *this* prediction without a heavier SHAP dependency.

## 14. System Architecture

```
User
  │
  ▼
Frontend UI (HTML/CSS/JS, Bootstrap)
  │  fetch() → JSON
  ▼
Flask Backend / REST API  (backend/app.py)
  │
  ▼
Data Validation & Preprocessing
  (backend/utils/validation.py → ml/feature_engineering.py → saved ColumnTransformer)
  │
  ▼
ML Model  (ml/model.pkl, loaded once at startup)
  │
  ▼
Risk Prediction  (Low / Medium / High + probability + top factors)
  │
  ▼
Database  (MySQL in production / SQLite locally — backend/database/db.py)
  │
  ▼
Result displayed on UI  (result.html + dashboard.html)
```

## 15. Frontend Architecture

- `index.html` — home/landing page, project intro, "Assess Loan Risk" CTA
- `assessment.html` — applicant intake form with client-side validation, calls
  `POST /api/predict`, stores the JSON response in `sessionStorage`, redirects to result
- `result.html` — reads the stored result, renders risk category, probability, class
  probabilities, top factors, and recommendation
- `dashboard.html` — calls `/api/dashboard`, `/api/model-performance`, `/api/applications`
  to render stat cards, a risk-distribution pie chart, a model-comparison bar chart,
  confusion-matrix/ROC images, feature importance, and the full application history table
- `css/style.css` — shared banking/finance design system (navy/gold ledger theme)
- `js/script.js` — shared navbar/footer rendering, `apiFetch()` helper, formatting utilities

## 16. Backend Architecture

- `backend/app.py` — Flask app; serves the frontend as static files and exposes the API
- `backend/database/db.py` — SQLite (MySQL-schema-compatible) data access layer
- `backend/database/schema_mysql.sql` — production MySQL DDL
- `backend/utils/validation.py` — request payload validation
- `backend/utils/predictor.py` — loads `model.pkl` + `preprocessor.pkl` once at startup,
  runs `feature_engineering.py` + the saved preprocessor, returns prediction + explanation
- `backend/routes/` — kept per the required project structure; routes are currently
  consolidated in `app.py` for this project's scope and can be split into blueprints later

## 17. API Documentation

All responses are JSON. Errors return `{"success": false, "error": "...", "details": [...]}`
with an appropriate HTTP status instead of a stack trace.

### `POST /api/predict`
Validates input, engineers features, runs the trained pipeline, stores the applicant +
prediction, and returns the result.

Request body (JSON):
```json
{
  "applicant_name": "Rahul Sharma",
  "age": 30,
  "gender": "Male",
  "marital_status": "Married",
  "education": "Graduate",
  "dependents": 1,
  "employment_status": "Salaried",
  "self_employed": "No",
  "applicant_income": 5000,
  "coapplicant_income": 2000,
  "loan_amount": 150000,
  "loan_term": 180,
  "credit_score": 720,
  "existing_loans": 1,
  "repayment_history": "Good",
  "property_area": "Urban"
}
```

Response (200):
```json
{
  "success": true,
  "applicant_id": 1,
  "applicant_name": "Rahul Sharma",
  "risk_category": "Low",
  "risk_icon": "🟢",
  "risk_probability": 82.4,
  "all_class_probabilities": {"Low": 0.824, "Medium": 0.15, "High": 0.026},
  "recommendation": "Loan application appears relatively low risk.",
  "top_factors": [{"factor": "Credit history", "value": 1, "importance": 1.28}],
  "model_used": "Logistic Regression"
}
```

### `POST /api/applicant`
Stores an applicant record without running a prediction (rarely needed directly, since
`/api/predict` already stores both).

### `GET /api/applications?limit=100`
Returns application history (applicant + latest prediction, most recent first).

### `GET /api/dashboard`
Returns aggregate counts (`total_applications`, `low_risk`, `medium_risk`, `high_risk`) and
the 10 most recent predictions.

### `GET /api/model-performance`
Returns the model comparison table, the selected best model + its metrics, before/after
tuning comparison, and global feature importance.

### `GET /api/health`
Simple liveness + "is the model loaded" check.

## 18. Installation & How to Run

### Prerequisites
- Python 3.10+

### Steps
```bash
# 1. Clone / unzip the project, then from the project root:
pip install -r requirements.txt

# 2. (Already done in this delivery, but to regenerate from scratch:)
cd dataset && python3 generate_dataset.py && cd ..

# 3. Train the models (writes ml/model.pkl, ml/preprocessor.pkl, comparison CSVs, plots)
cd ml && python3 train_models.py && cd ..

# 4. (Optional) print a readable evaluation report from the saved artifacts
cd ml && python3 evaluate_models.py && cd ..

# 5. Run the Flask app (serves both the API and the frontend)
cd backend && python3 app.py
```

Then open **http://localhost:5000/** in a browser.

> To run EDA plots: `cd ml && python3 eda.py` (writes to `ml/eda_outputs/`).

### Switching to MySQL
See §9 above and the docstring at the top of `backend/database/db.py`.

### Switching to real XGBoost / imbalanced-learn
See §5 above and the docstrings at the top of `ml/train_models.py` and `ml/smote_custom.py`.
